## SpecKit Workflow (Critical Section)

Nova uses the **SpecKit methodology** for specification-driven development. All features MUST be specified before implementation.

### Available Commands

| Command | Purpose | When to Use |
|---------|---------|-------------|
| [/speckit.specify](./claude/commands/speckit.specify.md) | Create feature specification from natural language | Start of every new feature |
| [/speckit.clarify](./claude/commands/speckit.clarify.md) | Ask up to 5 targeted clarification questions | When spec has ambiguities marked `[NEEDS CLARIFICATION]` |
| [/speckit.plan](./claude/commands/speckit.plan.md) | Generate technical design (research, data model, contracts) | After spec is clarified and approved |
| [/speckit.tasks](./claude/commands/speckit.tasks.md) | Generate dependency-ordered task list | After plan is complete |
| [/speckit.analyze](./claude/commands/speckit.analyze.md) | Validate cross-artifact consistency (read-only) | Before implementation or periodically |
| [/speckit.implement](./claude/commands/speckit.implement.md) | Execute all tasks from tasks.md | When ready to build the feature |
| [/speckit.checklist](./claude/commands/speckit.checklist.md) | Generate custom requirement quality checklists | Any time to validate spec quality |
| [/speckit.constitution](./claude/commands/speckit.constitution.md) | Update project governance document | When amending principles or constraints |

### Workflow Sequence

```
1. /speckit.specify "Feature description"
   → Creates: specs/[###-feature-name]/spec.md
   → Generates: User stories (P1/P2/P3), requirements (FR-###), success criteria
   → Output: Branch created, spec file with clarification questions

2. /speckit.clarify (if needed)
   → Resolves: Max 5 [NEEDS CLARIFICATION] markers in spec
   → Updates: spec.md with user-provided answers
   → Output: Fully specified feature ready for planning

3. /speckit.plan
   → Creates: research.md, data-model.md, contracts/, quickstart.md, plan.md
   → Validates: Constitution Check (ensures compliance with principles)
   → Output: Complete technical design

4. /speckit.tasks
   → Creates: tasks.md with phase-based organization
   → Organizes: By user story (P1 → P2 → P3), with [P] parallel markers
   → Output: Executable task list with dependencies

5. /speckit.analyze (optional)
   → Validates: Consistency across spec/plan/tasks
   → Reports: Gaps, conflicts, constitution violations
   → Output: Quality report (non-destructive)

6. /speckit.implement
   → Executes: All tasks from tasks.md in dependency order
   → Verifies: Checklists complete before starting
   → Output: Fully implemented feature with tests
```

### Branch Naming Conventions

```bash
feature/[###]-<short-name>    # New features (merge via PR)
fix/[###]-<short-name>        # Bug fixes (merge via PR)
spec/[###]-<short-name>       # Spec-only changes (merge directly)
prototype/[###]-<short-name>  # Exploratory code (max 1 week, see Principle 5)
spike/[###]-<short-name>      # Technical research (max 1 week)
```

**Important:** `[###]` is auto-generated by `/speckit.specify` based on existing branch/spec numbers.

## Constitution - Supreme Governance Document

**Location:** [.specify/memory/constitution.md](.specify/memory/constitution.md)
**Version:** 1.2.0 (last amended 2025-01-13)
**Authority:** Constitution supersedes all other documents. When in doubt, consult the constitution.

### The 7 Core Principles

| ID | Principle | Summary | Key Metric |
|----|-----------|---------|------------|
| 1 | **STUDENTS_FIRST** | Every decision prioritizes student benefit over administrative convenience | Student satisfaction >4.5/5 |
| 2 | **PRIVACY_FOUNDATION** | Minimal data collection, zero tracking, privacy-first architecture | Zero privacy incidents |
| 3 | **SIMPLICITY_FIRST** | Default answer to features is "no" unless proven student need | Feature adoption >30% or deprecate |
| 4 | **PERFORMANCE_FIRST** | <1s load times, 60fps UI, instant perceived feedback | Feed <1s cached, 60fps sustained |
| 5 | **SPEC_FIRST** | All features specified before implementation, prototypes allowed | 100% features have specs |
| 6 | **DESIGN_SYSTEM_STRICT** | Zero hardcoded values, design system constants enforced | Zero hardcoded color/spacing |
| 7 | **CONTENT_MODERATION** | Human moderation mandatory, school-appropriate content only | Queue <24h, <5% false positives |

### Critical Constraints From Constitution

**Privacy (Non-Negotiable):**
- Magic Link authentication via any valid email address (passwordless)
- Zero third-party tracking (no Google Analytics, Facebook SDK)
- Zero advertising ever
- Chat messages auto-delete after 24 hours
- GDPR compliance: Right to Access, Erasure, Data Portability, Rectification

**Performance Budgets (Strict):**
- Feed screen: <1 second cached, <3 seconds first load (4G)
- User interactions: <200ms perceived response time
- Sustained 60fps minimum (UI jank is P0 bug)
- Images: WebP format, max 200KB each
- APK size: <50MB (Android), IPA size: <60MB (iOS)

**Security Requirements:**
- Row-Level Security (RLS) policies on all Supabase tables (non-negotiable)
- Magic link expiration: 15 minutes
- Session management: 30-day refresh tokens
- HTTPS-only, TLS 1.3 minimum
- No sensitive data in logs

**Design System Enforcement:**
- All colors from `NovaColors` class (no `Color(0xFF...)` hex codes)
- All spacing from `NovaSpacing` class (no magic numbers)
- All typography from `NovaTypography` class
- All border radius from `NovaRadius` class
- Glassmorphism via `GlassContainer` widget only

### Anti-Goals (Permanent Constraints)

Nova will **NEVER:**
1. Become a social network with follower counts or influencer dynamics
2. Show advertisements or monetize student attention
3. Sell, share, or broker student data to third parties
4. Implement addictive engagement patterns (infinite scroll dopamine loops, notification spam)
5. Replace real human interaction (facilitates in-person events only)
6. Become a surveillance tool for administration or parents
7. Expand to other schools without explicit strategic decision and architecture redesign

**Violating any anti-goal requires creating a new project, not evolving Nova.**

## Technology Stack

### Required Stack (Non-Negotiable)

**Frontend:**
- **Language:** Dart (Flutter SDK 3.x+)
- **State Management:** Riverpod (mandated for consistency and testability)
- **UI Pattern:** Feature-first clean architecture

**Backend:**
- **Backend-as-a-Service:** Supabase Cloud
- **Database:** PostgreSQL 15+ (via Supabase)
- **Authentication:** Supabase Auth with Magic Link (passwordless)
- **Storage:** Supabase Storage (CDN-backed)
- **Realtime:** Supabase Realtime (WebSocket subscriptions)
- **Deployment:** Supabase Cloud (EU Frankfurt region for GDPR)

### Rationale for Stack Choices

- **Flutter/Dart:** Cross-platform (iOS + Android from single codebase), native 60fps performance, hot reload for rapid iteration
- **Riverpod:** Type-safe state management, compile-time safety, highly testable
- **Supabase Cloud:** Open-source Firebase alternative, full PostgreSQL power, zero DevOps during MVP, generous free tier (500MB DB, 1GB storage)
- **Magic Link:** Passwordless eliminates password reset flows, more secure (email as second factor), better UX for students
- **EU Frankfurt:** GDPR compliance requirement for Italian school with minor students

**⚠️ Critical:** No framework changes mid-project. Technology switches destroy momentum and create massive technical debt.

## Architecture Pattern

### Feature-First Clean Architecture

```
lib/
├── core/                    # Shared utilities, theme, constants
│   └── theme/              # Design system (NovaColors, NovaSpacing, NovaTypography, NovaRadius)
│       ├── nova_colors.dart
│       ├── nova_spacing.dart
│       ├── nova_radius.dart
│       ├── nova_typography.dart
│       └── app_theme.dart
├── features/               # Self-contained feature modules
│   └── eventi/             # Example: Events feature
│       ├── data/          # Supabase repositories, data sources
│       ├── domain/        # Models, entities, business logic
│       └── presentation/  # Screens, widgets, Riverpod providers
└── shared/                # Reusable widgets
    └── widgets/
        └── glass_container.dart  # Example: Glassmorphism effect widget
```

### Mandatory Architectural Rules

1. **Features are self-contained:** Minimal cross-feature imports
2. **Data layer Supabase-only:** No direct UI to database calls
3. **Presentation uses Riverpod exclusively:** No direct repository instantiation
4. **Shared widgets are pure presentation:** No business logic, only UI rendering
5. **Domain layer is framework-agnostic:** Can be tested without Flutter

## Testing Requirements

### Mandatory Tests (Must Have)

1. **Authentication complete flow:** Magic link generation → email verification → session creation → login success
2. **Event lifecycle:** Creation → moderation queue → approval → display in feed → interaction
3. **Supabase Row-Level Security policies:** Security tests verifying RLS rules work correctly
4. **Critical user paths:** Create event, like event, comment on event, join chat, view profile

### Recommended Tests (Nice to Have)

1. **Widget tests:** All shared components (GlassContainer, EventCard, etc.)
2. **Integration tests:** Complete user flows (onboarding → event creation → participation)
3. **Golden tests:** UI regression detection (screenshot comparison)

### Testing Philosophy

- **Test behavior, not implementation:** Avoid testing private methods or implementation details
- **Prefer integration tests over unit tests:** Test real user flows, not isolated functions
- **Visual testing via hot reload is valid:** Screenshot comparison tests are supplementary
- **Test coverage is not a goal:** Focus on critical paths and business logic

## High-Level Architecture

### Design System Structure

Nova uses a **strict design system** to ensure visual consistency. All UI values MUST come from constants:

```dart
// ✅ CORRECT - Use design system constants
Container(
  padding: EdgeInsets.all(NovaSpacing.medium),
  decoration: BoxDecoration(
    color: NovaColors.backgroundPrimary,
    borderRadius: BorderRadius.circular(NovaRadius.large),
  ),
  child: Text(
    'Event Title',
    style: NovaTypography.headingMedium,
  ),
)

// ❌ FORBIDDEN - Hardcoded values will fail code review
Container(
  padding: EdgeInsets.all(16),  // NO magic numbers
  decoration: BoxDecoration(
    color: Color(0xFF1A1A2E),  // NO hex color codes
    borderRadius: BorderRadius.circular(12),  // NO hardcoded radius
  ),
  child: Text(
    'Event Title',
    style: TextStyle(fontSize: 18, fontWeight: FontWeight.bold),  // NO inline styles
  ),
)
```

### State Management Pattern (Riverpod)

All state management MUST use Riverpod providers:

```dart
// ✅ CORRECT - Riverpod provider
final eventsProvider = FutureProvider<List<Event>>((ref) async {
  final repository = ref.read(eventRepositoryProvider);
  return repository.getApprovedEvents();
});

// In widget
class EventsFeed extends ConsumerWidget {
  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final eventsAsync = ref.watch(eventsProvider);
    return eventsAsync.when(
      data: (events) => EventsList(events: events),
      loading: () => CircularProgressIndicator(),
      error: (err, stack) => ErrorWidget(error: err),
    );
  }
}

// ❌ FORBIDDEN - Direct repository instantiation
class EventsFeed extends StatefulWidget {
  @override
  _EventsFeedState createState() => _EventsFeedState();
}

class _EventsFeedState extends State<EventsFeed> {
  final repository = EventRepository();  // NO direct instantiation
  // ...
}
```

### Supabase Integration Pattern

All data access MUST go through Supabase with Row-Level Security (RLS):

```dart
// ✅ CORRECT - Repository pattern with RLS
class EventRepository {
  final SupabaseClient _supabase;

  EventRepository(this._supabase);

  Future<List<Event>> getApprovedEvents() async {
    // RLS policy ensures only 'approved' events visible to students
    final response = await _supabase
        .from('events')
        .select()
        .eq('status', 'approved')
        .order('created_at', ascending: false);

    return (response as List).map((json) => Event.fromJson(json)).toList();
  }
}

// ❌ FORBIDDEN - Direct widget to database calls
class EventsFeed extends StatelessWidget {
  @override
  Widget build(BuildContext context) {
    final events = Supabase.instance.client  // NO direct DB access from UI
        .from('events')
        .select();
    // ...
  }
}
```

## GDPR Compliance Requirements

Nova serves minors (ages 14-18) in the EU, therefore GDPR compliance is **mandatory and non-negotiable**.

### Mandatory Rights Implementation

**Right to Access (Art. 15):** Users export all data in JSON format via Settings → Privacy → Download My Data

**Right to Erasure (Art. 17):** Users delete account via Settings → Privacy → Delete Account (irreversible after 30-day grace period)

**Right to Data Portability (Art. 20):** Export includes profile data, created events, comments, participation history

**Right to Rectification (Art. 16):** Users edit profile data directly in-app

**Consent Management (Art. 7):** Clear opt-in for optional data (e.g., Instagram handle) with withdrawal option

### Data Retention & Deletion

- **Deleted accounts:** Soft-deleted (30-day grace period), then hard-deleted from production database
- **Backup purging:** Deleted data removed from automated backups after 90 days (Supabase retention policy)
- **Chat messages:** Auto-deleted after 24 hours (ephemeral by design, GDPR compliant by default)

### Documentation Required

- **Privacy Policy:** Published at nova.galileimoro.edu.it/privacy (accessible without login)
- **In-app link:** Settings → Privacy → Privacy Policy
- **Updates:** Privacy Policy updated before each release if data practices change

## Emergency Override Procedure

From [Constitution v1.2.0 - Governance](.specify/memory/constitution.md):

If adhering to a principle creates **existential risk to project survival**:

1. **Document the crisis:** Write detailed explanation of circumstances and why principle blocks solution
2. **Propose temporary exception:** Specify explicit expiration date (maximum 3 months)
3. **Create amendment proposal:** Draft permanent solution to resolve conflict
4. **Transparency requirement:** Emergency exceptions require community announcement
5. **Limitation:** No more than 1 active emergency exception at a time

**Example:** Server costs €200/month, no funding model, principle forbids ads
- **Temporary exception:** Allow non-tracking sponsor logos for 3 months
- **Permanent solution:** Implement school partnership funding OR premium alumni features

**Emergency override does NOT:**
- Replace constitutional amendment process (still required for permanent change)
- Permit violations of legal requirements (GDPR, child safety laws)
- Allow violations of multiple principles simultaneously
- Extend beyond 3 months
